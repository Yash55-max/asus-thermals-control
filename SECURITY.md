# Security Policy & Threat Model

Thermals manages platform thermal profiles, CPU energy preferences, fan cooling, and battery charging thresholds. Because writing to Linux `/sys` kernel nodes requires root privileges, this document defines the project's security architecture and threat model.

---

## Privileged Execution Model

Thermals employs a **defense-in-depth privilege separation** model:

```
[ Unprivileged Desktop User ]
           │
           ├── 1. Desktop Session DBus (power-profiles-daemon via powerprofilesctl)
           │      └── Zero root / sudo privileges required for active desktop user.
           │
           └── 2. Privileged Helper (/usr/local/sbin/asus-thermal-profile)
                  ├── Root-owned (0755, root:root)
                  ├── Scoped sudoers rule (/etc/sudoers.d/asus-thermal-control)
                  └── Strict argument whitelisting & bounds enforcement
```

1. **Default Unprivileged Operation**:
   On standard desktop Linux systems running `power-profiles-daemon`, platform thermal profiles are adjusted through the desktop session bus without root passwords or sudo access.

2. **Scoped Helper Script (`asus-thermal-profile`)**:
   For headless daemons, battery charge threshold adjustments, and direct ACPI sysfs writes, an allowlisted helper is installed to `/usr/local/sbin/asus-thermal-profile`.

---

## Threat Model & Security Controls

### 1. Inode & Directory Ownership
- **Requirement**: The helper script and its parent directory (`/usr/local/sbin`) must be owned by `root:root` with mode `0755`.
- **Mitigation**: Unprivileged users cannot modify, replace, symlink, or rename the script. `install-helper.sh` verifies root ownership and non-world-writable permissions.

### 2. Sudoers Rule Scoping
- **Requirement**: Sudoers must never allow arbitrary binaries or unvalidated commands.
- **Mitigation**: The rule generated by `install-helper.sh` names the exact binary:
  ```sudoers
  username ALL=(root) NOPASSWD: /usr/local/sbin/asus-thermal-profile
  ```
  Every execution is validated using `visudo -cf` before placement in `/etc/sudoers.d/`.

### 3. Argument Whitelisting & Path Sanitization
- **Arbitrary Path Traversal Prevention**:
  The helper rejects arbitrary paths. Fan PWM paths are strictly regex-validated against `/sys/class/hwmon/hwmon[0-9]+/pwm[1-9]` and canonicalized via `readlink -f`. Arbitrary paths (e.g. `/sys/devices/*`, `/etc/*`, `../../`) are rejected with exit code 2.
- **Enum & Numeric Bounds Checking**:
  - `profile`: Strictly limited to `quiet|balanced|performance|low-power|cool|balanced-performance`.
  - `boost`: Strictly limited to `on|off|0|1`.
  - `epp`: Strictly limited to `power|balance_power|balance_performance|performance`.
  - `charge-limit`: Strictly limited to integers between `50` and `100`.
  - `fan`: PWM values are strictly limited to integers `0-255` or enum `auto`.

### 4. Thermal Safety Rails
- **Emergency Fan Override**: If monitored temperatures exceed 80°C or hardware critical trip points, manual fan throttling is overridden and fans are forced to maximum / automatic firmware curves.
- **Automatic Failsafe on Exit**: When the application exits or receives termination signals (`SIGINT`, `SIGTERM`), all PWM fan controls are restored to firmware automatic curves (`pwm*_enable = 2`).
